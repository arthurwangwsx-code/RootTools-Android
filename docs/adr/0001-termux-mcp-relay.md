# ADR-0001 — Termux MCP Relay Boundary

- Status: **accepted**
- Date: 2026-08-20
- Owners: RootTools
- Related: `docs/20-termux-developer-runtime.md`

## Context

RootTools needs an Agent / MCP integration without turning the Android application into a public
root daemon or exposing an arbitrary `su` terminal. Termux is a better Linux execution plane for
Python, SSH, Git and long-running user-space processes, while RootTools remains the typed Android
privileged control plane.

The current MCP specification is `2026-07-28`. Its core is stateless JSON-RPC 2.0, each request
carries protocol/client capability metadata, `server/discover` replaces the old initialization
handshake, and Streamable HTTP requires a new POST per message plus matching
`MCP-Protocol-Version`, `Mcp-Method`, and request-specific `Mcp-Name` headers.

## Decision

### 1. Execution ownership

```text
Agent / MCP Client
       ↓
Termux MCP relay
       ↓ typed actions only
RootTools ActionRouterReceiver
       ↓
Controller / Repository
       ↓
RootShell / Android framework
```

The relay never receives a generic command string that is forwarded to `sh`, `bash`, `su`,
`Runtime.exec`, or RootTools `RootShell`.

The first MCP tool catalog is deliberately small:

- `get_device_status`
- `set_performance_mode`
- `ensure_root_adb`
- `run_diagnostic`
- `freeze_app`
- `enable_app`

Adding a tool requires first adding or reusing a typed RootTools automation action and reviewing
its scope/risk. There is no `execute_shell`, `run_command`, `reboot`, or arbitrary Termux task tool.

### 2. Protocol version

The generated relay targets MCP `2026-07-28` only. It implements:

- `server/discover`
- `tools/list`
- `tools/call`
- stdio newline-delimited JSON-RPC
- stateless HTTP POST `/mcp` with JSON responses

It does not emulate the removed session/`initialize` behavior. Backward compatibility may be added
later only if a concrete client requires it and protocol tests cover both eras.

### 3. Network exposure

Allowed HTTP bind modes are exactly:

```text
loopback   → 127.0.0.1
tailscale  → RootTools-reported Tailscale IPv4 in 100.64.0.0/10
```

The relay has no `0.0.0.0`, LAN, mobile-data, or arbitrary bind-address option. Failure to resolve a
valid Tailscale address is a hard failure; there is no fallback to a broader interface.

The initial HTTP port is fixed to `8765`. Port customization is deferred until there is a validated
configuration model and collision handling.

For remote development, **stdio over an authenticated SSH/Tailscale path is preferred** because it
does not open an additional MCP listener. Tailscale HTTP is an explicit alternative.

### 4. Authorization and credentials

Two credentials are intentionally separate:

1. **RootTools automation credential** — generated for client `termux-mcp`, stored hashed by
   RootTools, embedded only in the generated private relay artifact, and limited to MCP-required
   RootTools scopes.
2. **Relay bearer credential** — protects the optional HTTP edge and can be rotated independently.

The bearer gate is a private pre-shared transport control for this personal device workflow. MCP
authorization is optional at the protocol level, but the standard HTTP authorization profile is
OAuth-based. Therefore RootTools does **not** describe this pre-shared bearer mechanism as an
implementation of MCP OAuth authorization. If third-party/public interoperability later requires
standard MCP authorization, Protected Resource Metadata and the normative OAuth flow must be added
as a separate feature rather than pretending this token is equivalent.

The relay and RootTools each enforce a 60 request/minute backstop. Credentials are never written to
the Root action audit, Termux task audit, diagnostic stdout, or normal UI logs.

### 5. Installation and lifecycle

The relay is generated by RootTools and contains a version + SHA-256 identity. Stable Termux builds
with `RUN_COMMAND` can receive it only through a fixed managed installer task whose destination is:

```text
~/roottools/agent/roottools_mcp.py
```

The installer accepts stdin only from RootTools-generated artifacts, writes atomically with mode
`0700`, and verifies SHA-256 afterward.

On Google Play Termux builds without `RUN_COMMAND`, RootTools can export the same artifact for an
explicit manual install. RootTools will not use root to write into Termux private data as a shortcut.

Starting the HTTP relay is explicit. RootTools does not enable MCP relay boot persistence by default.
The managed stop action validates the pid still belongs to `roottools_mcp.py` before sending a signal.

### 6. Android process policy

RootTools itself does not add a long-running MCP foreground service, socket server, or public daemon.
The Linux relay process belongs to Termux. This keeps RootTools battery/lifecycle behavior unchanged
and preserves the existing privilege boundary.

## Rejected alternatives

### Expose `RootShell.execute(command)` over MCP

Rejected. It collapses all authorization scopes into unrestricted root code execution and bypasses
Controller validation, audit semantics, rollback policy, and package/input validation.

### Bind MCP to `0.0.0.0`

Rejected. It would silently expose a privileged device-control surface to Wi-Fi/mobile interfaces.

### Root-write files directly into `/data/data/com.termux`

Rejected. It couples RootTools to Termux internals, breaks app ownership/SELinux assumptions, and
uses root where the official Termux bridge or explicit user share is sufficient.

### Auto-enable sshd/MCP at boot

Rejected as a default. Persistence is a distinct user decision and must remain independently
auditable/revocable.

## Consequences

Positive:

- Agent capability grows without introducing arbitrary privileged shell execution.
- Termux remains replaceable as an execution backend.
- Remote exposure has a narrow, testable interface policy.
- The same semantic RootTools actions are reused by UI, ADB, CLI, and Agent paths.

Trade-offs:

- The first tool catalog is intentionally smaller than a terminal.
- Google Play Termux needs manual relay/CLI file installation until it exposes an official external
  execution bridge or a separately validated local SSH backend is available.
- OAuth-compatible MCP HTTP authorization is not implemented in this phase; standard-auth clients
  should use stdio/SSH or wait for that dedicated feature.

## Verification requirements

Before declaring remote Agent support fully validated:

1. generated Python passes syntax validation;
2. stdio `server/discover`, `tools/list`, and representative `tools/call` pass protocol fixtures;
3. HTTP rejects missing/wrong protocol/method/name headers;
4. HTTP rejects invalid bearer credentials;
5. loopback mode listens only on `127.0.0.1`;
6. tailscale mode refuses to start without a valid RootTools-reported `100.64.0.0/10` address;
7. tool catalog contains no generic shell/exec action;
8. RootTools scoped-client rate limit is effective;
9. stop refuses to kill a pid whose command line is not the RootTools relay;
10. Samsung SM-S908E + Termux real-device round-trip is recorded in the delivery ledger.
